03 · 리눅스 기초

    
파일 권한 — rwx와 755·644

    
권한 문자열 10칸은 “누가(소유자·그룹·기타) 무엇을(읽기·쓰기·실행) 할 수 있는가”를 압축한 표기입니다. 아래 계산기에서 비트를 직접 켜고 끄면서 숫자와 문자가 어떻게 대응하는지 몸으로 익히세요.

  


  

    
권한 문자열 읽는 법


 -   rwx   r-x   r-x
 │    │     │     └── 기타 사용자 (other)
 │    │     └──────── 그룹 (group)
 │    └────────────── 소유자 (user / owner)
 └─────────────────── 종류: - 파일, d 디렉토리, l 심볼릭 링크

  

  
r=4, w=2, x=1을 더해 한 자리 숫자를 만듭니다. rwx=7, r-x=5, rw-=6, r--=4, ---=0.

챌린지

      
—

      

    

    
파일과 디렉토리에서 x의 뜻이 다릅니다. 파일의 x는 “실행 가능”, 디렉토리의 x는 “그 안으로 cd해서 통과 가능”. 그래서 디렉토리에 r만 있고 x가 없으면 이름 목록은 보여도 안으로 들어가거나 내부 파일 상세는 볼 수 없습니다.

  


  
실습에서 실제로 바꾼 결과

  

    
파일 → 600 / 디렉토리 → 700


$ touch test.txt
$ ls -l test.txt
-rw-rw-r-- 1 jmlee jmlee 0 Aug  3 01:15 test.txt   # before

$ chmod 600 test.txt
$ ls -l test.txt
-rw------- 1 jmlee jmlee 0 Aug  3 01:15 test.txt   # after

$ ls -ld test
drwxr-xr-x 2 jmlee jmlee 6 Aug  3 01:14 test       # before (755)

$ chmod 700 test
$ ls -ld test
drwx------ 2 jmlee jmlee 6 Aug  3 01:14 test       # after (700)

  

  
함정
디렉토리를 볼 때 ls -l만 쓰면 그 안의 목록이 나옵니다. 디렉토리 자체의 권한을 보려면 -d를 붙여 ls -ld 디렉토리로 확인하세요. 또, touch로 만든 파일이 644가 아니라 664로 나오는 것은 시스템 umask 차이일 뿐 정상입니다.


  
기호 표기와 소유권

  

    
명령의미

    
      
chmod u+x file소유자(u)에게 실행 권한 추가

chmod a+r file전체(a)에게 읽기 권한 추가

      
chown 사용자:그룹 file소유자·그룹 변경 (보통 sudo 필요)

04 · Docker

    
이미지와 컨테이너

    
Docker를 이해하는 첫 갈림길은 이미지와 컨테이너가 다른 것이라는 사실입니다. 이미지는 읽기 전용 설계도, 컨테이너는 그 설계도로 찍어낸 실행 중인 실체입니다. 하나의 이미지로 컨테이너를 몇 개든 만들 수 있습니다.

  


  

    
이미지 (Image)
변하지 않는 읽기 전용 템플릿. 레이어가 쌓인 형태로 저장되며 docker images로 조회합니다. 이미지를 지우려면 docker rmi.

    
컨테이너 (Container)
이미지를 실행한 결과. 자체 쓰기 레이어를 갖고, 지우면 그 쓰기 레이어도 함께 사라집니다. docker ps로 조회, docker rm으로 삭제.

리소스 — docker stats

  
캡처 요령
docker stats는 기본적으로 화면이 계속 갱신되는 대시보드라 로그·스크린샷으로 남기기 어렵습니다. --no-stream을 붙이면 현재 값을 한 번만 찍고 종료되어 증거 수집에 적합합니다.

  

    
실행 중인 컨테이너가 있어야 의미 있는 값이 나옴


$ docker run -d --name stats-demo ubuntu sleep infinity
7aeb016abfab2737562bac45b4962622f8692de287a9eb6f52ffceeca538fa

$ docker stats --no-stream
CONTAINER ID   NAME         CPU %   MEM USAGE / LIMIT     MEM %   NET I/O        PIDS
7aeb016abfab   stats-demo   0.00%   1.719MiB / 345.8GiB   0.00%   2.9kB / 126B   1

  


  
중지 — 종료 코드가 알려주는 것

  


$ docker stop stats-demo
stats-demo

$ docker ps -a --filter name=stats-demo
CONTAINER ID   IMAGE    COMMAND            STATUS                 NAMES
7aeb016abfab   ubuntu   "sleep infinity"   Exited (137) …       stats-demo

  

  
docker stop은 컨테이너에 SIGTERM을 보내고, 일정 시간 안에 안 죽으면 SIGKILL을 보냅니다. 137 = 128 + 9 — SIGKILL(9)로 종료됐다는 뜻입니다. sleep infinity가 SIGTERM을 무시했기 때문에 결국 강제 종료된 것이죠. 정상적으로 SIGTERM에 응답하는 프로세스라면 Exited (0)이 됩니다.

07 · Docker

    
exec vs attach — PID 1의 수명

    
컨테이너의 수명은 PID 1의 수명과 같습니다. 이 한 문장이 두 명령의 모든 차이를 만듭니다. attach는 그 PID 1에 직접 붙고, exec는 옆에 새 프로세스를 하나 더 만듭니다.

[docker attach]

레이어 캐시 — 순서가 빌드 속도를 결정한다

  
RUN·COPY는 각각 하나의 레이어입니다. 앞 레이어가 그대로면 Docker는 그 아래를 캐시에서 재사용합니다. 그래서 자주 바뀌지 않는 것(의존성 설치)을 앞에, 자주 바뀌는 것(소스 코드)을 뒤에 두면 코드만 고쳤을 때 빌드가 훨씬 빨라집니다.

포트 매핑

    
컨테이너는 호스트와 분리된 자체 네트워크 영역을 가집니다. 컨테이너 안에서 NGINX가 80번을 듣고 있어도 호스트의 브라우저는 그 포트에 직접 닿을 수 없습니다. -p <호스트포트>:<컨테이너포트>는 그 사이에 통로를 뚫는 선언입니다.

  


  
비유
호스트는 아파트 건물, 컨테이너는 각 세대, 컨테이너 포트는 세대 내 방 번호, 호스트 포트는 1층 무인 택배함 번호입니다. 택배기사(사용자)는 세대 안방으로 직접 못 들어가므로 “1층 8080번 택배함에 넣으면 101호 안방(80번)으로 전달된다”는 규칙을 만드는 것이 포트 매핑입니다.

같은 호스트 포트로 두 번 실행해 보세요. 호스트에서 한 포트는 한 프로세스만 쓸 수 있어 port is already allocated 에러가 납니다. 반대로 컨테이너 포트는 80으로 똑같아도 호스트 포트만 다르면 몇 개든 동시에 뜹니다 — 이것이 포트 매핑이 필요한 두 번째 이유입니다.

  


  
포트 매핑이 필요한 이유 3가지

  

    
1 · 외부 노출
매핑하지 않으면 컨테이너 서비스는 호스트 밖에서 접근할 수 없습니다. 컨테이너 네트워크 안에 갇혀 있게 됩니다.

    
2 · 다중 실행
컨테이너 포트 80을 호스트 8080·8081에 각각 매핑하면 같은 이미지를 동시에 여러 개 띄울 수 있습니다.

    
3 · 선택적 노출 = 보안
웹(80)만 매핑하고 DB(5432)·Redis(6379)는 매핑하지 않으면 내부 서비스는 컨테이너 네트워크 안에서만 접근 가능해집니다.

Docker Compose

    
길게 외워 치던 docker run 옵션이 문서화된 실행 설정으로 바뀝니다. 여러 컨테이너를 함께 띄우고, 서로를 서비스 이름으로 찾게 만드는 것이 Compose의 진짜 가치입니다.

  


  

    
Lab 11app/compose.yaml — 서비스 그래프를 직접 띄우고 내리기

    

      

        
        
        
        
        
      

      

      
터미널

    

    
probe는 IP를 전혀 모르는 채 http://web/health라고만 씁니다. Compose가 만든 네트워크 안에서 서비스 이름이 곧 호스트명이 되기 때문입니다 — 이것이 서비스 디스커버리입니다.

  


  

    
app/compose.yaml


services:
  web:
    build:
      context: .
    image: workstation-web:1.0
    ports:
      - "127.0.0.1:${WORKSTATION_HOST_PORT:-8080}:80"   # ← 환경 변수 + 기본값

  probe:
    image: alpine:3.23
    depends_on:
      web:
        condition: service_healthy                       # ← web이 healthy 될 때까지 대기
    command:
      - sh
      - -c
      - while true; do wget -qO- http://web/health; sleep 15; done
    restart: unless-stopped

  


  

    
127.0.0.1 바인딩
ports를 127.0.0.1:8080:80으로 적으면 내 컴퓨터에서만 접근 가능합니다. 같은 네트워크의 다른 기기에는 실습 서버가 노출되지 않습니다.

    
service_healthy
Dockerfile의 HEALTHCHECK가 여기서 쓰입니다. probe는 web이 실제로 응답 가능해진 뒤에야 시작합니다 — “떴다”와 “준비됐다”는 다릅니다.

    
${VAR:-기본값}
환경 변수가 없으면 8080을 씁니다. 설정과 코드의 분리 — 파일을 고치지 않고 실행 시점에 포트를 바꿀 수 있습니다.

    
restart: unless-stopped
컨테이너가 죽으면 자동 재시작하되, 사용자가 명시적으로 멈춘 경우엔 그대로 둡니다.

  


  
운영 명령 루틴

  

    
명령하는 일

    
      
docker compose up -d정의된 서비스 전부를 백그라운드로 기동 (필요하면 빌드까지)

      
docker compose ps서비스별 상태·포트 확인 (healthy 여부 포함)

      
docker compose logs --tail=5서비스 로그 확인. 서비스명을 붙이면 그것만

      
docker compose down컨테이너 + 네트워크까지 정리

      
WORKSTATION_HOST_PORT=9090 docker compose up -d web환경 변수로 호스트 포트를 바꿔 기동

Git은 내 컴퓨터에서 변경 이력을 기록·관리하는 소프트웨어이고, GitHub는 그 저장소를 인터넷에 올려 공유·협업하는 웹 플랫폼입니다. Git은 내 책상 위 개인 연습장, GitHub는 그 내용을 올려 공유하는 블로그입니다.

  


  

    
구분GitGitHub

    
      
정체소프트웨어 / 도구웹 서비스 / 플랫폼

      
위치내 컴퓨터 (로컬)클라우드 서버 (원격)

      
인터넷필요 없음필수

      
핵심 기능commit, branch, merge, logpush, pull, Pull Request, Issue

      
대체제SVN, MercurialGitLab, Bitbucket

터미널

    

    
파일은 작업 트리 → 스테이징 → 로컬 저장소 → 원격 순으로 이동합니다. git add까지만 하고 commit을 안 하면 이력에 남지 않고, commit까지만 하고 push를 안 하면 GitHub에는 아무것도 안 올라갑니다.

  


  
이 저장소를 실제로 연결한 순서

  

    
초기화 → 커밋 → 원격 등록 → push


$ git init -b main                          # 기본 브랜치명을 main으로 지정하며 초기화
$ git config user.name "JmLeeRoom"
$ git config user.email "…@gmail.com"       # 커밋마다 기록되는 정보

$ git add .
$ git commit -m "Initial commit: mission checklist and setup guide"

$ git remote add origin https://github.com/JmLeeRoom/codyssey_first_mission.git
$ git remote -v
origin  https://github.com/JmLeeRoom/codyssey_first_mission.git (fetch)
origin  https://github.com/JmLeeRoom/codyssey_first_mission.git (push)

$ git push -u origin main                    # -u: 이후엔 git push 만으로 충분
 * [new branch]      main -> main

  


  
자주 막히는 두 지점
    
① 원격에 이미 커밋이 있는 경우 — GitHub 저장소 생성 시 README 자동 생성을 켰다면 히스토리가 달라 push가 거부됩니다. git pull origin main --allow-unrelated-histories로 먼저 합친 뒤 push하세요.

    
② 비밀번호가 거부되는 경우 — GitHub는 2021년부터 계정 비밀번호로 HTTPS push를 허용하지 않습니다. 브라우저 인증 흐름을 따르거나 Personal Access Token을 발급해 비밀번호 자리에 입력합니다. 토큰 값은 절대 스크린샷·로그에 남기지 마세요.

  


  
보안 — 문서에 남기면 안 되는 것

  

    
절대 금지
Personal Access Token, 비밀번호, SSH 개인키, 인증 코드, 실제 값이 담긴 .env

    
마스킹 권장
이메일 로컬파트([MASKED]@gmail.com), 내부 호스트명, 개인 절대 경로

    
커밋 전 점검
grep -rniE 'token|secret|password' .로 훑고, 스크린샷도 눈으로 한 번 더 확인

    
노출됐다면
파일에서 지우는 것만으로는 Git 히스토리에 남습니다. 즉시 재발급이 원칙입니다.
