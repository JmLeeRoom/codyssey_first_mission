## 절대 경로와 상대 경로

```bash
$ realpath hello.txt
/home/jmlee/Project/codyssey/codyssey_first_mission/practice/cli-demo/hello.txt

$ ls -l ./hello.txt              # 상대 경로 (현재 위치 기준)
$ ls -l "$(pwd)/hello.txt"       # 절대 경로 (/ 부터 시작)
```

| 구분 | 예시 | 특징 |
| --- | --- | --- |
| 절대 경로 | `/home/jmlee/Project/.../hello.txt` | `/`부터 시작. 어디서 실행하든 항상 같은 파일 하나만 가리킨다 |
| 상대 경로 (같은 폴더) | `hello.txt`, `./hello.txt` | 현재 위치가 그 폴더일 때만 유효 |
| `..` 사용 | `../../Dockerfile` | 하위 폴더에서 상위의 파일을 가리킴 |

**한 문장 정리**: 절대 경로는 GPS 좌표처럼 위치가 불변이고, 상대 경로는 "여기서 두 블록 앞"처럼 **내가 서 있는 곳이 기준**이다. 스크립트를 다른 디렉터리에서 실행하면 상대 경로는 깨지지만 절대 경로는 그대로 동작한다.

## 파일 권한(r/w/x)과 755·644 표기

권한 문자열은 10칸으로 읽는다.

```
 -   rwx   r-x   r-x
 │    │     │     └── 기타 사용자 (other)
 │    │     └──────── 그룹 (group)
 │    └────────────── 소유자 (user/owner)
 └─────────────────── 종류: - 파일, d 디렉터리, l 심볼릭 링크
```

r=4, w=2, x=1을 더해 한 자리 숫자를 만든다.

- **755 = `rwxr-xr-x`** — 소유자는 전부(7), 그룹·기타는 읽기+실행(5). 디렉터리의 표준값.
- **644 = `rw-r--r--`** — 소유자는 읽기·쓰기(6), 그룹·기타는 읽기만(4). 일반 문서 파일의 표준값.

**파일과 디렉터리에서 `x`의 뜻이 다르다.** 파일의 `x`는 "실행 가능", 디렉터리의 `x`는 "그 안으로 `cd`해서 통과 가능"이다. 그래서 디렉터리에 `r`만 있고 `x`가 없으면 이름 목록은 보여도 안으로 들어가거나 내부 파일 상세 정보는 볼 수 없다. (직접 확인: [`permissions-guide.md`](./permissions-guide.md))

## 포트 매핑이 필요한 이유

컨테이너는 호스트와 분리된 자체 네트워크 영역을 가진다. 컨테이너 안에서 NGINX가 80번을 듣고 있어도 호스트의 브라우저는 그 포트에 직접 닿을 수 없다. `-p <호스트포트>:<컨테이너포트>`는 그 사이에 통로를 뚫는 선언이다.

**필요한 이유 3가지**

1. **외부 노출** — 매핑하지 않으면 컨테이너 서비스는 호스트 밖에서 접근할 수 없다.
2. **포트 충돌 회피 / 다중 실행** — 호스트에서 한 포트는 한 프로세스만 쓴다. 하지만 컨테이너 포트 80을 호스트 8080·8081에 각각 매핑하면 같은 이미지를 동시에 여러 개 띄울 수 있다 (`web-demo`/`web-demo-2`로 직접 확인함).
3. **선택적 노출 = 보안** — 필요한 포트만 매핑하면 나머지 내부 서비스는 컨테이너 네트워크 안에서만 접근 가능해진다.

> **비유** — 호스트는 아파트 건물, 컨테이너는 각 세대, 컨테이너 포트는 세대 내 방 번호, 호스트 포트는 1층 무인 택배함 번호다. "1층 8080번 택배함에 넣으면 101호 안방(80번)으로 전달된다"는 규칙을 만드는 것이 포트 매핑이다.

## Docker 볼륨(영속 데이터)

컨테이너의 쓰기 레이어는 컨테이너와 함께 사라진다. **이름 있는 볼륨**은 Docker가 관리하는 호스트 영역에 데이터를 두고 컨테이너 경로에 연결하므로, 컨테이너의 생명 주기와 데이터의 생명 주기가 분리된다. 실제로 컨테이너를 삭제한 뒤 새 컨테이너에서 같은 볼륨을 연결해도 데이터(와 체크섬)가 그대로였다 ([`volume-guide.md`](./volume-guide.md)).

## Git과 GitHub의 역할 차이

- **Git** — 내 컴퓨터(로컬)에서 소스 변경 이력을 기록·관리하는 버전 관리 소프트웨어. 인터넷 없이도 `commit`, `branch`, `merge`가 모두 동작한다.
- **GitHub** — Git 저장소를 인터넷에 올려 공유·협업하는 웹 플랫폼. `push`/`pull`, Pull Request, Issue 같은 협업 기능을 제공한다.

| 구분 | Git | GitHub |
| --- | --- | --- |
| 정체 | 소프트웨어/도구 | 웹 서비스/플랫폼 |
| 위치 | 내 컴퓨터(로컬) | 클라우드 서버(원격) |
| 인터넷 | 필요 없음 | 필수 |
| 핵심 기능 | commit, branch, merge, log | push, pull, Pull Request, Issue |

**비유**: Git은 내 책상 위 개인 연습장(혼자 쓰고 지우고 되돌림), GitHub는 그 내용을 올려 공유하는 블로그(댓글=코드 리뷰, 퍼가기=Fork)다.
